# Evidence-Based PS

一个用于研究生 Personal Statement（PS）和 Statement of Purpose（SOP）的 Codex Skill。

它不会一上来就替申请人生成一篇看似完整的文书，而是先核实经历、区分个人贡献与团队成果、筛选真正有证明力的细节，再设计故事线或修改文本。它尤其适合解决以下问题：

- 不知道哪些经历值得写进 PS；
- 项目细节很多，但不知道哪些细节真正有用；
- 文书像扩写版简历，缺少思考和转变；
- Why School 与前文割裂，只是在罗列课程和教授；
- 担心数字、奖项、职责或技术结论写得不准确；
- 需要从中文素材形成英文 PS，同时保持事实和个人表达。

## 核心原则

- **先证据，后写作**：事实、职责和结果不清楚时，不急着润色。
- **选择深度，不堆砌细节**：围绕一个关键决定、意外结果、失败、权衡或观察展现思考过程。
- **区分归属**：明确区分“我做了”“团队做了”和“项目获得了”。
- **不替申请人编答案**：缺失信息会被标出，不能验证的内容不会包装成事实。
- **按当前任务工作**：如果只要求追问、选材、故事线或事实检查，就不会擅自生成整篇文书。
- **不套固定模板**：不会默认所有人都适合五段式、800 词或科研型开头。

### Windows

```powershell
git clone https://github.com/chenxi1251/evidence-based-ps.git "$env:USERPROFILE\.codex\skills\evidence-based-ps"
```

```bash
git clone https://github.com/chenxi1251/evidence-based-ps.git ~/.codex/skills/evidence-based-ps
```

安装后重新启动 Codex 或开启一个新对话，使 Codex 重新读取可用技能。

## 怎么调用

最可靠的方式是在提示词中明确写出技能名称：

```text
使用 $evidence-based-ps 帮我准备计算机硕士申请的 PS。
先追问和核实经历，不要直接写正文，也不要替我补充事实。
```

技能也可以在请求与其适用范围明显匹配时自动触发。不过在重要任务中，建议显式写出 `$evidence-based-ps`。

你不必一次性提供全部材料。可以从不同阶段开始：

```text
使用 $evidence-based-ps，把下面三段经历分为核心素材、辅助素材和只适合放 CV 的素材。
```

```text
使用 $evidence-based-ps，围绕这段项目经历连续追问我。直到能确认问题、行动、个人贡献、结果、反思和项目匹配度为止。
```

```text
使用 $evidence-based-ps，根据已确认的素材设计故事线。只说明每一段的任务，不写正式文章。
```

```text
使用 $evidence-based-ps，检查这份 PS 的事实归属、数字口径、空泛表达和 Why School，不要整体重写。
```

## 一个真实感的交互场景

下面是一个虚构但符合真实申请过程的示例。它展示的是交互方式，而不是可直接复制的文书素材。

### 第一轮：用户只提供项目概况

**用户：**

> 我申请数据科学硕士。做过一个面向校内政策问答的 RAG 项目，四人团队，我主要负责检索部分。请先不要写 PS，看看还缺什么信息。

**Codex：**

> 目前只能确认项目主题、团队规模和你的大致职责，还不足以判断它是否适合作为 PS 主线。我先追问会影响选材的部分：
>
> 1. 原系统具体遇到了什么问题？是召回不到相关内容，还是生成答案不可靠？
> 2. “负责检索”具体包括哪些由你完成的工作？请把个人工作与团队工作分开。
> 3. 项目中有没有一个结果打破了你原来的预期，并促使你改变方案？
> 4. 最终效果如何衡量？请说明指标、测试数据和对比对象。
> 5. 这段经历让你产生了什么进一步想研究或学习的问题？

这里不会追问所有实现细节。它优先寻找能够证明个人判断和能力的关键转折。

### 第二轮：用户补充证据

**用户：**

> 系统需要从约 400 份校内政策文件中检索依据。最初只用稠密检索，但涉及精确条款编号的查询经常失败。我负责建立检索评测集、分析错误并实现混合检索。团队其他成员负责文档解析、生成模块和前端。
>
> 我把失败查询分类后发现，语义查询适合稠密检索，但条款编号和专有名词更依赖关键词匹配，于是加入 BM25，并用开发集确定融合权重。在提前隔离的 60 条测试查询上，Recall@5 从 0.68 提高到 0.79。这个过程让我意识到，评测不只是汇报结果，也会直接影响系统设计。我想继续学习更系统的检索和模型评测方法。

### 第三轮：技能整理证据，而不是立刻写作文

**Codex：**

> 这段经历已经具备作为核心素材的条件：
>
> - **问题**：单一稠密检索难以处理精确条款编号和专有名词。
> - **你的贡献**：建立评测集、分析失败样本、实现 BM25 与稠密检索融合，并选择融合权重。
> - **关键转折**：没有把低召回简单归因于模型能力，而是通过错误分类发现不同查询需要不同检索信号。
> - **结果**：在提前隔离的 60 条测试查询上，Recall@5 从 0.68 提高到 0.79。
> - **认识变化**：评测从“项目结束后的报告工具”变成了“决定系统结构的依据”。
> - **深造连接**：希望系统学习检索、评测以及针对不同输入自适应选择方法。
>
> 还需要确认两个问题：这 60 条查询由谁标注，以及融合代码是否由你独立完成。这两点会影响结果可信度和个人贡献的表述。确认后，我再判断它适合承担哪一段的任务。

这个阶段的产物是可核查的“证据地图”。如果信息仍有缺口，技能会继续追问；如果新增细节已经不会改变招生官对经历的判断，就会停止追问。

### 第四轮：从证据转为故事线

事实确认后，可以继续要求：

```text
现在使用 $evidence-based-ps 设计故事线。请说明每一段使用什么证据、承担什么任务，以及招生官读完应得到什么结论；同时检查段落之间是否重复。
```

可能得到的结构不是“把项目从头到尾复述一遍”，而是：

1. 用对不同输入为何需要不同方法的兴趣提出学术问题；
2. 用稠密检索的失败和错误分析证明问题来源真实；
3. 用混合检索的设计与测试结果证明分析能够转化为方案；
4. 从评测驱动设计的认识自然引出需要补足的研究训练；
5. 将课程、项目资源和职业方向分别对应到前文已经出现的需求。

## 支持的工作阶段

| 阶段 | 可以怎样提问 |
| --- | --- |
| 素材采集 | “连续追问这段经历，但不要问不会影响文书的琐碎细节。” |
| 经历筛选 | “按核心素材、辅助素材、CV-only 分类并说明原因。” |
| 故事线设计 | “说明每段任务、证据和希望招生官得出的结论。” |
| 事实核查 | “核对数字、时间、职责、奖项和团队成果的归属。” |
| Why School | “根据我的能力缺口核查课程或研究资源，避免官网式吹捧。” |
| 起草与修改 | “只使用已确认事实起草；保留我的逻辑和表达习惯。” |
| 翻译与语言检查 | “准确翻译专业词汇，检查长句和模板化表达，不改变事实。” |

## 它不会做什么

- 不会替用户虚构项目细节、研究兴趣或职业目标；
- 不会把团队成果全部写成个人贡献；
- 不会因为经历听起来有名或有奖就默认写进 PS；
- 不会承诺录取结果或所谓的 AIGC 检测分数；
- 不适用于 CV、推荐信或普通学术论文写作。
